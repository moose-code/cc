# Independent security audit, main branch

Scope: `main` at `3bc342d`, `src/`, `script/`, `script/config/mainnet.json`, and the specified live contract interactions at mainnet fork block 26,127,622. `docs/FLOW.md` section 9 controls where earlier text differs. This review did not treat previous reviews or their tests as evidence without checking the implementation and rerunning tests. No contract or deploy script was changed.

## Summary

**Critical: 0. High: 0. Medium: 1. Low: 1. Info: 0.** The Core deploys at 24,415 runtime bytes, 161 bytes below the 24,576 byte limit. I would defer launch until the floor raise procedure is corrected and the unresolved full-suite failures are explained: the documented `REPRICE=1` path can miss a newly composed statement and let a bidder buy at 110% of cost after the owner has set a 200% floor. This is a procedure and script failure around an accepted onchain behavior, not a bypass of the reserve that existed when the auction was created. The second finding makes postflight print incorrect constructor arguments after mutable values change. I found no demonstrated nonowner drain of the pots or below-reserve sale on the pinned fork; the full suite did not pass, so this is not a safety certification.

### A01: a floor raise can omit a listing

**What breaks.** `SetSettings._openListings` reads `heldStatements()` and selects the listings to reprice before the owner transaction. Composition remains permissionless. A statement composed after that read has a valid old reserve but is absent from the batch. Also, the script's `SEND=1` path broadcasts `setSettings` and each reprice as separate transactions, so a bid can land between them. The underlying Core behavior, that an existing house reserve remains valid until repriced, is explicitly accepted in `docs/FLOW.md` 9.2 and `docs/ARCHITECTURE.md` item 2. This finding is that the prescribed procedure does not reliably close that interval.

**Preconditions and impact.** At least 80 credits are in the ETH pile, or can be supplied before the floor raise. The owner prepares `REPRICE=1`; an attacker or keeper composes after the script reads the listing IDs. The owner raises `saleFloorBps`; the omitted listing keeps its old reserve and has no first bid yet. A bidder pays the old reserve and, if not outbid, receives the statement after the real house auction. At launch controller settings, an age-zero reserve is 110% of cost. For a raise to 200%, the difference is 90% of statement cost, or 45% of the new floor, per missed statement. A competing bidder may raise the final price.

**Proof.** `test/audit/FloorRaiseRace.t.sol` runs against the real Credits, Statements, Core-owned house, and artcoins stack on block 26,127,622. It reads an empty reprice snapshot while the ETH pile has 80 credits, composes, raises the floor to 20,000 bps, applies the snapshot, bids the old reserve, settles the house auction, and collects exactly that sale price. The test passes on the fork.

**Fix.** The runbook and script must stop claiming an offchain snapshot reprices every open listing. A Safe batch prevents a bid between the owner's own calls, but cannot include a statement composed after its snapshot. To guarantee the raised floor, add an onchain transition that closes this race, such as a temporary composition pause that is active through the raise and reprice, or a house bidding path that checks the current floor. The Core has only 161 runtime bytes of headroom, so an onchain fix may require moving more logic into the linked library. If that contract change is not chosen, explicitly treat old reserves as live until every listing is checked again and refrain from asserting an immediate hard floor after a raise.

### A02: verification arguments drift after deployment

**What breaks.** `coreConstructorArgs` encodes the original owner from the config but reads `core.controller()` and `core.settings()` from current storage. The controller and settings are owner mutable. `printVerifyInputs` presents that encoding as the Core constructor arguments for verification, although those inputs are fixed in the creation transaction.

**Preconditions and impact.** Any settings update or controller replacement before postflight prints the verification data. The printed arguments then differ from the deployment transaction and can cause source verification to fail or send the operator to debug the wrong build. No asset leaves the Core. `OWNER_CHANGED=1` and `SETTINGS_CHANGED=1` permit postflight use after such changes, so this is a supported operational state.

**Proof.** `test/audit/PostflightInputs.t.sol` deploys the full system on the pinned fork, records `coreConstructorArgs`, changes `saleFloorBps` from 7,500 to 8,000, and proves the printed encoding changes. The test passes.

**Fix.** Encode the constructor's original values from the signed launch config or the creation transaction. Display live values separately.

## Not checked

- The two audit proof tests passed on the pinned fork with Foundry 1.8.0 and 1.8.1. `forge build --skip test --sizes` passed. The full suite with Foundry 1.8.1 and static test linking finished with **705 passed, 29 failed, 8 skipped**. Normal test linking in both installed Foundry versions failed during generated test compilation, so static linking was required for that full run. The failed tests include resume/library address assumptions, gas-meter assertions, and a gas-burning controller regression. These failures prevent a claim that the configured release gate is green.
- The default phase 2 invariant fixture reverted during setup with an `OutOfGas` trace. With Foundry's block gas limit disabled, its 24-run, 80-call campaign started and failed two of 15 invariants on 1 wei reimbursement-cap mismatches, one on compose and one on exit. Phase 1 invariants also reported the compose mismatch. I did not isolate whether the 1 wei is a contract accounting defect or a test harness measurement defect; no asset-loss finding is inferred from it.
- The fork is fixed at block 26,127,622. Changes to the live factory, auction fee, stack enablement, or RPC state after that block were not verified; launch preflight must run on current mainnet state.
- No transaction was broadcast and no private key was used. The actual production signer, nonce, relay ordering, and Safe batch behavior were not exercised.
- No additional exhaustive state-space campaign was run.
